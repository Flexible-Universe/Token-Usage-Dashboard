# Export chain

The dashboard only reads files. The data directory is filled by the scripts in
this directory: they query `ccusage` and `rtk`, check the output and write it
atomically into the data directory. No step overwrites an existing file before
the new output has been checked.

## Platforms

The chain runs on macOS, Linux and Windows. It is plain Python 3.11+ from the
standard library; the date arithmetic is Python's, not that of a particular
`date(1)`. The former Bash scripts and the launchd templates are gone; the
scheduled jobs are generated by `install.py` in the root directory.

## The scripts

| File | Purpose |
|---|---|
| `ccusage-export.py` | Calls `ccusage` in three modes |
| `rtk-export.py` | Calls `rtk gain`, one run per day is enough |
| `exportlib.py` | Shared helpers of both: binary search, logs, status call |
| `ccusage-check.py` | Checks a fresh export against the existing file |
| `ccusage-merge.py` | Layers an export onto an existing archive file |
| `rtk-merge.py` | Distributes the rtk export across monthly files and merges them |
| `export-status.py` | Writes the status files of a run |

The three modes of `ccusage-export.py`:

- `ccusage-export.py daily` rewrites the current month, plus, during the first
  three days of a month, the previous month once more. Affects `YYYY-MM.json`
  in the root directory and in `projects/`.
- `ccusage-export.py weekly` archives blocks and sessions into
  `blocks/YYYY-Www.json` and `sessions/YYYY-Www.json`.
- `ccusage-export.py monthly` freezes the completed previous month.

`rtk-export.py` has no modes. It fetches the complete history
(`rtk gain --all --format json`) and merges it into `rtk/YYYY-MM.json`. The `rtk/` directory is created only after
a successful probe (`rtk gain --format json` returns JSON), so a host without
a working `rtk` never starts to expect rtk data. `install.py` applies the same
lookup and probe before it sets up `rtk/` and the `rtk-daily` job.

Both scripts take their settings as options as well:

| Option | Script | Takes precedence over |
|---|---|---|
| `--data-dir PATH` | both | `CCUSAGE_DATA_DIR` or `RTK_DATA_DIR` |
| `--lookback-days N` | `ccusage-export.py` | `CCUSAGE_LOOKBACK_DAYS` |
| `--ccusage-bin PATH` | `ccusage-export.py` | `CCUSAGE_BIN` and the search |
| `--rtk-bin PATH` | `rtk-export.py` | `RTK_BIN` and the search |

The options exist because `cmd.exe`, PowerShell and the Windows Task
Scheduler cannot put a variable in front of a command. An option beats the
variable, the variable beats the default.

## Status files

Every run of `ccusage-export.py` and `rtk-export.py` leaves a record in
`<data>/status/`, written by `export-status.py`, which the script calls from a `finally`
block, so an abort is recorded too:

- `<job>.last.json` after every run, `<job>.ok.json` additionally when the
  exit code is 0, with identical content. `<job>` is `daily`, `weekly`,
  `monthly` or `rtk`.
- Content: `schema` (1), `job`, `startedAt` and `finishedAt` as
  `YYYY-MM-DDTHH:MM:SSZ` in UTC, `exitCode`, `targets` and, for `weekly`
  only, `lookbackDays`.
- `targets` lists the files with `file` (path relative to the data
  directory) and `result` (`ok`, `frozen`, `aborted` or `failed`). `rtk`
  has the single target `rtk/`.
- The helper validates its input and exits with code 2 before writing
  anything. A failure of the helper never changes the exit code of the run.

The dashboard evaluates these files, see `docs/06-checks.md`. Format and the
reason for two files: `docs/02-data-sources.md`.

## Why the weekly run is mandatory

Blocks and sessions come from the JSONL files under `~/.claude`, whose history
only reaches back about 31 days. If the weekly run fails for longer than a
month, that period is irrecoverably lost. The gap opens earlier than that: after
`CCUSAGE_LOOKBACK_DAYS`, because the weekly window then no longer reaches the
last successful run. The dashboard reports it. Daily and project data, by contrast,
can be regenerated at any time — they come from a source that does not expire.

## Regressions: strict, merge, freeze

An export containing less than the existing file would delete data. How that
should be judged depends on the run.

- `strict` — a regression is an error, the existing file stays as it is. For
  the current month, which can only grow; if it shrinks, something is wrong.
- `merge` — the export is layered onto the existing file instead of replacing
  it. For the rolling weekly window, whose start moves on with every run and
  would otherwise take the day that fell out with it. The file can then only
  grow.
- `freeze` — a regression means: the archive is more complete than what
  `ccusage` can still produce today. The file stays, the run counts as
  successful. For completed previous months.

A regression can be allowed deliberately: `CCUSAGE_ALLOW_SHRINK=1`.

## Environment variables

| Variable | Meaning | Default |
|---|---|---|
| `CCUSAGE_DATA_DIR` | data directory for `ccusage-export.py` | platform default, see below |
| `CCUSAGE_BIN` | path to the `ccusage` binary | searched for |
| `CCUSAGE_LOOKBACK_DAYS` | overlap of the weekly window in days | `14` |
| `CCUSAGE_SEARCH_DIRS` | directories searched for `ccusage` before `PATH`; also read by `install.py` | per platform, see below |
| `CCUSAGE_ALLOW_SHRINK` | `1` allows a regression | unset |
| `RTK_DATA_DIR` | data directory for `rtk-export.py` | platform default, see below |
| `RTK_BIN` | path to the `rtk` binary | searched for |
| `RTK_SEARCH_DIRS` | directories searched for `rtk` before `PATH`; also read by `install.py` | per platform, see below |

The two `*_SEARCH_DIRS` lists are separated by the platform's path separator:
a colon on macOS and Linux, a semicolon on Windows. A set but empty value
means "no fixed directories", only `PATH`.

Default data directory:

| Platform | Path |
|---|---|
| macOS | `~/Library/Application Support/Claude-Code-Usage` |
| Linux | `${XDG_DATA_HOME:-~/.local/share}/claude-code-usage` |
| Windows | `%LOCALAPPDATA%\Claude-Code-Usage` |

Both scripts search for the binary themselves, because every scheduler starts
with its own sparse `PATH` (launchd with `/usr/bin:/bin:/usr/sbin:/sbin`), and
nvm, Volta or Homebrew are invisible there. The order is: option, variable,
the fixed directories, then `PATH`. A named path that is no longer
executable (an nvm upgrade removes the old node directory) is passed over
and the search decides. The fixed directories:

| Platform | `ccusage` | `rtk` |
|---|---|---|
| macOS | `~/.nvm/versions/node/*/bin` (newest first), `~/.volta/bin`, `~/.bun/bin`, `~/.npm-global/bin`, `~/.local/bin`, `/opt/homebrew/bin`, `/usr/local/bin` | `/opt/homebrew/bin`, `/usr/local/bin`, `~/.cargo/bin`, `~/.local/bin` |
| Linux | as macOS up to `~/.local/bin`, then `/usr/local/bin`, `/home/linuxbrew/.linuxbrew/bin`, `/usr/bin` | `~/.cargo/bin`, `~/.local/bin`, `/usr/local/bin`, `/home/linuxbrew/.linuxbrew/bin` |
| Windows | `%APPDATA%\npm`, `%LOCALAPPDATA%\pnpm`, `%LOCALAPPDATA%\Volta\bin`, `~\.bun\bin` | `~\.cargo\bin` |

On Windows each name is tried with the extensions from `PATHEXT`, because npm
installs `ccusage.cmd` and cargo installs `rtk.exe`. `ccusage-export.py`
puts the directory of the binary it found in front of `PATH` for the call,
because `ccusage` needs `node`, which lies next to it. If the search finds
nothing, the run aborts with a message and a status file — it never runs
silently into nothing.

`install.py` pins the interpreter and the paths of `ccusage` and `rtk` it
found into every job (`--ccusage-bin`, `--rtk-bin`), so the job decides
exactly as the installer did.

## Logs

One file per job under `<data>/logs/`: `daily.log`, `weekly.log`,
`monthly.log`, `rtk.log`, each trimmed to the last 2000 lines. The messages
are German. A line `ABBRUCH` ("aborted") always means: the target file was
left unchanged. Besides these, the scheduler's own output lands in
`launchd-<job>.out`/`.err` (macOS), `systemd-<job>.out`/`.err` (systemd) or
`cron-<job>.out` (cron). The Windows jobs run under `pythonw.exe`, which has
no console; everything a run has to say is in its own log.

## Where the scripts run

The files in this directory are the source, not the place of deployment.
`install.py` in the root directory copies them to `<data>/bin`, and the
scheduled jobs call those copies. The detour is deliberate: a work in progress
should not drag the nightly export down with it. If something changes here,
`./install.sh --force` (`install.cmd --force` on Windows) brings the copies
up to date; if they differ without `--force` being set, the installer
reports it and leaves them alone. A release package always replaces them,
because it brings a consistent set.

Copies of the former `ccusage-export.sh` and `rtk-export.sh` left in
`<data>/bin` are reported as obsolete and not deleted; the jobs no longer
call them.

## Scheduled jobs

`install.py` creates them; `--with-jobs` from a clone, by default from a
release package. Times are local:

| Job | Call | Time |
|---|---|---|
| `ccusage-daily` | `ccusage-export.py daily` | daily at 04:00 |
| `rtk-daily` | `rtk-export.py` | daily at 04:15 |
| `ccusage-weekly` | `ccusage-export.py weekly` | Sundays at 04:30 |
| `ccusage-monthly` | `ccusage-export.py monthly` | on the 1st at 05:00 |

The scheduler follows the platform, `--scheduler` overrides it:

| Scheduler | Platform | What is written | Missed runs |
|---|---|---|---|
| `launchd` | macOS | `~/Library/LaunchAgents/<prefix>.<job>.plist`, default prefix `com.<user>` | after sleep, not after power-off |
| `systemd` | Linux, when a user manager answers | `token-usage-dashboard-<job>.service` and `.timer` in `~/.config/systemd/user` | caught up (`Persistent=true`) |
| `cron` | Linux without systemd | a marked block in the user's crontab | not caught up |
| `schtasks` | Windows | tasks in the folder `\Token-Usage-Dashboard\`, started with `pythonw.exe` | caught up (`StartWhenAvailable`) |

`--label-prefix` replaces the prefix in every case. systemd user timers and
the Windows tasks run only while the user is logged in; for systemd,
`loginctl enable-linger` lifts that. After a longer break without catch-up,
start the weekly run by hand. `--remove-jobs` removes the jobs again; the
data directory stays untouched.

## Where the data directory may live

Not in a folder that a sync client or the system guards: on macOS not under
`~/Documents`, `~/Desktop` or iCloud Drive, because TCC denies the launchd
process access there; nowhere in Dropbox; on Windows not in OneDrive. The
export then aborts with a permission error that looks like a program bug.
The platform default directories are safe. `install.py` checks the data and
the application directory and reports a risky location.

## Name collision for rtk

`rtk` in this context is the token proxy with the command `rtk gain`. There is
a second tool of the same name, `reachingforthejack/rtk` (Rust Type Kit). If
that one is on the path, the export appears to run through, and the mix-up
only shows in the dashboard as an empty RTK tab. Check beforehand:

```bash
which rtk
rtk gain      # must show a savings statistic, not a type error
```
